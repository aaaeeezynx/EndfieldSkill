# 《终末地》技能释放助手：产品方案草稿

## 1. 产品目标

解决一个很具体的痛点：线上教程通常只展示一套固定队伍，但玩家实际拥有的角色不一定是同一套。

本产品的核心不是“再做一个视频教程”，而是把教程抽象成：

1. 基于已拥有角色的队伍筛选；
2. 可解释的技能释放顺序；
3. 每一步的触发时机与等待条件；
4. 每个角色的装备与属性达标要求；
5. 缺少角色时的替代方案。

## 2. MVP 产品范围

### 首版必须完成

- 角色库存录入：按角色、命座/突破、武器、装备、等级登记。
- 关卡/目标选择：关卡、敌人、阶段、难度、机制标签。
- 队伍推荐：根据已有角色生成 1~3 个候选队伍，并解释取舍。
- 技能时间轴：按“准备、启动、增益窗口、爆发、恢复/循环”输出释放顺序。
- 时机提示：显示触发条件，例如“敌人破韧后”“护盾消失后”“能量满后”。
- 装备清单：每个角色显示推荐武器、套装、主属性优先级、最低达标线。
- 替代建议：角色缺失或装备不达标时，展示替换角色/降级方案。
- 分享与保存：保存方案，导出为图片或文本教程。

### 首版暂缓

- 精确逐帧战斗模拟；
- 自动读取游戏账号；
- 全量视频识别；
- 复杂 DPS 模拟器；
- 多人社区投稿与公开榜单。

这些功能可以后续加入，但不应阻塞第一版解决“我该按什么顺序放技能”的核心问题。

## 3. 产品架构图

架构采用“前端体验层 + 推荐服务 + 版本化资料库 + 内容运营管线”四层结构。

### 架构分层

#### A. 前端体验层

- 首页：选择已拥有角色、选择目标内容。
- 队伍页：候选队伍、队伍评分、角色缺口。
- 技能页：时间轴、当前步骤、触发条件、取消/切人提示。
- 装备页：角色装备要求、替代方案、资源优先级。
- 设置页：数据来源、显示模式、分享设置。

#### B. 推荐服务层

- 角色库存过滤器：先筛出可用角色。
- 队伍组合评分器：综合元素/职业覆盖、协同、循环稳定性、操作复杂度。
- 技能时序规划器：把技能标签和条件编排成可执行的步骤序列。
- 装备需求规划器：根据角色定位输出武器、套装、主属性、最低阈值。
- 解释与置信度：说明“为什么推荐”，并标识资料完整度。

#### C. 游戏资料库

- 角色资料：基础属性、定位、突破/命座、技能入口。
- 技能资料：类型、能量、冷却、持续时间、作用标签、触发条件。
- 敌人与关卡资料：弱点、阶段、破韧/护盾、危险窗口、机制标签。
- 装备资料：武器、套装、主属性、副属性、获取途径、替代品。
- 版本资料：游戏版本、生效日期、变更记录、资料可信度。

#### D. 内容运营管线

- 资料采集：社区 Wiki、官方公告、玩家测试、结构化表格。
- 人工校验：字段审核、版本对比、冲突标记。
- 发布：JSON/数据库发布，前端按版本拉取。
- 反馈闭环：用户纠错、使用数据、低置信度样本回流。

### 推荐数据流

```text
用户库存 + 目标关卡
        |
        v
角色过滤 -> 队伍评分 -> 技能时序 -> 装备要求
        |             |           |
        +-------------+-----------+
                      |
                      v
              结果 + 依据 + 置信度
```

## 4. User Flow

### 主流程

1. 用户进入产品。
2. 选择或导入已拥有角色。
3. 选择目标关卡、敌人、阶段和难度。
4. 系统筛选可用队伍并生成候选方案。
5. 系统输出技能释放顺序、时机与装备要求。
6. 用户检查角色或装备缺口，调整队伍。
7. 用户查看“当前要做什么”的简化执行视图。
8. 保存、分享或导出教程。

### 分支流程

- 资料缺失：提示缺失字段，让用户手动补全后重算。
- 角色不全：优先给替代角色，再给“降配版”时间轴。
- 装备不达标：显示优先补齐哪一件、哪个属性、达到什么阈值。
- 用户不满意：回到队伍调整，不重新开始整个流程。

## 5. 推荐引擎的 MVP 规则

首版不需要一开始做成黑盒 AI，建议用“规则 + 评分 + 可解释结果”的方式：

### 队伍评分

- 必要覆盖：主输出、增益/减益、生存/治疗、破韧/控制等角色定位。
- 协同加成：元素/阵营/职业组合、能量循环、Buff 覆盖。
- 操作复杂度：技能数量、切人次数、时机窗口长度。
- 资料置信度：字段完整度和版本匹配度。

### 时序规划

把技能效果抽象成标签，例如：

- `buff_self`
- `buff_team`
- `debuff_enemy`
- `break_shield`
- `burst_damage`
- `survival`
- `energy_gain`

规划器按以下骨架排序：

1. 准备：开启长持续时间的团队增益。
2. 启动：放置减益、控制或破韧前置。
3. 窗口：确认目标进入可爆发状态。
4. 爆发：按能量、冷却、持续时间输出主技能。
5. 循环：补能量、治疗、护盾或等待下一窗口。

每一步都输出：

- 角色；
- 技能名；
- 为什么现在放；
- 触发条件；
- 等待多久；
- 是否需要切人；
- 可接受的替代操作。

## 6. 需要准备的资料

这是本产品是否可靠的关键，优先级从高到低如下。

### P0：没有就无法推荐

- 角色列表与定位；
- 每个技能的类型、能量、冷却、持续时间、效果标签；
- 常见关卡/敌人/阶段与关键机制；
- 角色可用的武器、套装、主属性优先级；
- 玩家已拥有角色、武器、装备和养成状态。

### P1：影响推荐质量

- Buff/Debuff 的具体覆盖率和叠层规则；
- 敌人破韧、护盾、无敌、转阶段条件；
- 技能前摇/后摇、取消窗口、切人时间；
- 不同难度下的数值差异；
- 装备替代品的可接受阈值。

### P2：影响长期体验

- 用户常用队伍和操作习惯；
- 玩家反馈的“更稳/更快/更简单”偏好；
- 版本更新差异；
- 热门关卡与高频失败点。

建议以结构化 JSON/CSV 为第一版资料格式，不要先把它塞进前端代码里。

## 7. 技术栈建议

### 推荐栈：适合小团队快速上线

- 前端：Next.js + React + TypeScript。
- UI：Tailwind CSS + shadcn/ui（或现有设计系统）。
- 状态：Zustand；角色库存优先 localStorage，登录后同步云端。
- 后端/API：Next.js Route Handlers，先不做独立服务。
- 数据库：Supabase（Postgres + Auth + Storage）。
- 资料版本：JSON schema + Postgres 表版本字段。
- 部署：Vercel；资料文件可放 CDN。
- 测试：Vitest（规则/评分/时序规划）、Playwright（主流程）。

### 什么时候升级

- 推荐逻辑变得复杂：拆出 Python FastAPI 服务。
- 需要大量用户数据与协作：加入 Redis/任务队列/后台管理。
- 需要模拟战斗：引入专门的战斗模拟引擎，而不是继续堆前端 if/else。

## 8. 最小数据模型

### Character

```json
{
  "id": "char_001",
  "name": "角色名",
  "element": "元素",
  "role": "输出/辅助/生存/破韧",
  "rarity": 5,
  "breakthrough": 2,
  "signature": "角色专属标签"
}
```

### Skill

```json
{
  "id": "skill_001",
  "characterId": "char_001",
  "type": "ultimate",
  "energyCost": 80,
  "cooldown": 18,
  "duration": 8,
  "tags": ["buff_team", "burst_damage"],
  "conditions": ["enemy_break_window"]
}
```

### EquipmentRequirement

```json
{
  "characterId": "char_001",
  "weapon": "推荐武器",
  "set": "推荐套装",
  "mainStats": ["暴击率", "攻击力"],
  "minimum": { "level": 80, "setPieces": 4 },
  "fallback": ["替代武器", "替代套装"]
}
```

## 9. 需要你确认的三个产品假设

1. 第一版优先做“队伍推荐 + 技能时间轴 + 装备清单”，还是先做“队伍筛选器”？
2. 目标内容先覆盖哪些模式：普通关卡、Boss、活动关、深境/高难、日常循环？
3. 你希望首版完全本地可运行、无需账号，还是从一开始支持云端保存与分享？

在这些答案确认前，架构可以按上述方案继续细化，但数据表和 UI 首页需要据此裁剪。
